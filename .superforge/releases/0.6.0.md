# 0.6.0 (2026-11-21)

Jobs: changes to the app's data that someone starts on purpose, a dry run
first, as code in the codebase run by the server, never a script against
production. Claude starts them through the MCP as the person who let it
in, once they've seen the dry run.

- **Jobs**, machinery: `source/backend/jobs/`. `defineJob` (`define.ts`)
  takes a name, a description, the input's zod schema, `plan`, the dry run,
  which reads only and answers what it would change, and `run`, a
  workflow's body, a step per batch. `index.ts`'s `JOBS` lists them, and
  `backend/workflows/index.ts`'s `WORKFLOWS` now registers each one's
  workflow (`job-<name>`) beside the features' own. Routes
  (`routes.ts`), for the business's own: `GET /api/jobs`, each job and
  what it takes as JSON Schema, and `POST /api/jobs/:name` with
  `{ input }`, the dry run, or `{ input, dry_run: false }`, which starts
  it and answers the run's ID. A copy's own jobs go in its features'
  `jobs.ts`, listed in `JOBS`. How to tell a copy already has it:
  `source/backend/jobs/` exists.
- **`prune-sessions`**, the template's example job
  (`source/backend/auth/jobs.ts`): deletes the sessions that have run out,
  500 at a time, with `countExpiredSessions` and `deleteExpiredSessions`,
  new in `backend/auth/sessions.ts`.
- **The MCP's instructions** (`source/backend/mcp/index.ts`) tell Claude to
  change many rows through a job, dry run first and started only once the
  person says so, never a route called in a loop.
