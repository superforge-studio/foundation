# 0.12.0 (2026-11-22)

A write and the work it means land together: a run is queued inside the
write's own transaction, so it's queued if and only if the write commits.
Workflows can start on events or run on a cron schedule, and plumbing can
stay off the Workflows screen. And other services' webhooks have a place to come in, at
`/api/webhooks/<source>`, kept as they came, checked, and turned into
events.

**It changes how three things already there work**, each below: the
sign-up notice is queued by `signIn`'s transaction rather than started by
`auth/routes.ts`; the `Workflow` type gains `on`, `quiet` and `schedule`,
so a copy that builds one outside `defineWorkflow` adds them; and the
API's context gains `webhook_sources`, so a copy's code that builds the
variables by hand adds it.

- **Queueing a run with a write**, machinery:
  `source/backend/workflows/queue.ts`. `queueWorkflow(transaction,
  workflow, input, { id })` puts a run on its queue as part of the
  transaction, through DBOS 5.3's `enqueueInTransaction` on the
  transaction's own connection, since DBOS's queue is in the app's
  database. Handed the pool, it opens a transaction of its own. Its input
  is checked against the workflow's first, and a workflow not in
  `WORKFLOWS` throws. It reads the pg client from Drizzle's transaction at
  runtime (`connectionOf`), which its test pins, so a Drizzle upgrade that
  moves it fails there. `engine.ts` exports `APPLICATION` and
  `knownWorkflows()`, and `process.ts` holds the queueing client
  (`queueing`), which opens no connection of its own. How to tell a copy
  already has it: `source/backend/workflows/queue.ts` exists.
- **Events**, machinery: `source/backend/workflows/events.ts`'s
  `EVENTS`, each event by its name, `<record>-<verb>`, with a zod schema
  of what it carries, and `queueEvent(transaction, name, data, { id })`,
  which queues a run of every workflow that's `on` it, each named
  `<workflow>-<event id>`, and writes nothing when no workflow is. The one
  event is `user-signed-up`. A copy declares its own events there as its
  first workflow needs each.
- **`on` and `quiet` in `defineWorkflow`**, machinery:
  `source/backend/workflows/define.ts`. `on` names the events that start a
  workflow, typed to those whose data fits its input; `quiet: true` keeps
  its runs off the Workflows screen unless one fails (`runs.ts`'s
  `worthListing`, and `engine.ts`'s `runs()`, which then finds the runs
  worth listing a page of 200 at a time without their inputs). The
  `Workflow` type gains `on` and `quiet`, so a copy that builds one by
  hand, outside `defineWorkflow`, adds them.
- **`schedule` in `defineWorkflow`**, machinery: a cron schedule, in
  UTC, that DBOS fires the workflow on by itself, for a workflow whose
  input is `scheduled_input` (`{ scheduled_at }`, `define.ts`), which
  TypeScript holds it to. `engine.ts`'s `applySchedules` makes DBOS's
  schedules (DBOS 5.3's `applySchedules`, kept in its tables) follow
  `WORKFLOWS` as DBOS launches: one per scheduled workflow, named for it,
  onto its queue, with a moment missed while no process ran run once the
  next launches, and any schedule no workflow has deleted. Each moment's
  run is `sched-<workflow>-<moment>`, so it runs once.
  `scheduledFunction` hands DBOS a workflow's registered function.
  `tests/schedules.test.ts` checks every schedule is one DBOS runs, since
  one it refuses as the workflows launch is only logged. The `Workflow`
  type gains `schedule`. The workflows README's "On a schedule" says when
  a schedule fits and when a runner does.
- **The sign-up notice starts on an event**, a starting point:
  `tell-team-of-sign-up` (`source/backend/users/workflows.ts`) is
  `on: ["user-signed-up"]`, which `signIn` (`source/backend/auth/sign-in.ts`)
  queues in its own transaction when it makes someone new, named for them,
  so the run's id is `tell-team-of-sign-up-<user id>`, as before.
  `source/backend/auth/routes.ts` no longer starts it (`tellTeam` is
  gone). A copy that changed the notice, or where its sign-up starts,
  keeps its own and takes the event where it fits.
- **Webhooks in**, machinery: `source/backend/webhooks/`, with its
  README. `POST /api/webhooks/:source`, mounted in `backend/index.ts`
  ahead of the check for another site's forms, takes a delivery from a
  source in `sources.ts`'s `SOURCES` (none, as the template ships), on
  `context.var.webhook_sources`: kept as it came first, its signature
  checked (401 `bad-signature`, 503 `unconfigured`), its body read (400
  `unreadable`), and its events queued with its outcome in one
  transaction (200). A source that isn't listed is 404, keeps nothing, and
  is logged as a miss (`backend/misses/`, 0.10.0's), a warning when it's
  signed like a webhook. `standardWebhooksSource` and `standard.ts` check a
  Standard Webhooks signature, as Resend's are. A body is at most 2 MB.
  The API's context gains `webhook_sources` (`backend/context.ts`), so a
  copy's code that builds the variables by hand adds it, and `testApi()`
  hands none unless a test gives its own. **Schema**:
  `internal.webhook_deliveries` (`source/database/schema.ts`), with its
  outcome's check from `source/utilities/webhooks.ts`'s
  `WEBHOOK_OUTCOMES`. Generate the copy's migration
  (`pnpm database:generate --name=webhook-deliveries`); there's no SQL by
  hand. It's in the seed's `UNSEEDED`.
- **Pruning the deliveries**, machinery: `source/backend/webhooks/prune.ts`,
  30 days (`KEEP_DELIVERIES_FOR`), by `prune-webhook-deliveries`
  (`source/backend/webhooks/workflows.ts`), a quiet workflow on a schedule,
  each hour on the hour, listed in `WORKFLOWS`: the template's example of
  both.
- **Tests**, machinery: `testApi()` answers `queued()`, the runs a write
  queued, read back through DBOS's client
  (`source/backend/workflows/tests/support/queued.ts`'s `queuedRuns`). A
  test that read a sign-up's notice from `started` reads it from
  `queued()` now.
- **Docs**: `source/backend/workflows/README.md`, "Queueing a run with a
  write" (what goes in a write's transaction, what in a workflow, and why
  a step calls an operation rather than the app's own API), "Events" and
  "Quiet workflows"; `workbench/writing-code.md`; `CLAUDE.md`.
