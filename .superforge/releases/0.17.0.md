# 0.17.0 (2026-11-23)

A remembered visitor's IP address is kept again, on their visit, for 90
days. Infra kept it until analytics moved into the app in 0.7.0, which
left it out by default rather than by decision. A visitor the site doesn't
remember still has no address kept, since one beside the day's hash would
undo it, so `VISITOR_MODE` decides whose is kept: everyone's who hasn't
declined in `remember`, only those who accepted in `ask` (and `ask-in-eu`,
where it asks), and nobody's in `never`.

- **The column**, machinery. **Schema**: `analytics_visits.ip_address`
  (`inet`, nullable, `source/database/schema.ts`), with a partial index
  on `started_at` where it isn't null,
  `analytics_visits_ip_address_started_at_index`, which finds the
  addresses old enough to blank. `recordVisit`
  (`source/backend/visits/record.ts`) sets it as a visit starts, only for
  a remembered visitor, through `addressToKeep` (`visitors.ts`): an IPv4
  address written as IPv6 (`::ffff:203.0.113.9`) is kept as the IPv4 one,
  and anything Postgres's `inet` wouldn't take, like an address with a
  zone, is kept as null. Every caller of `recordVisit` gets it, a copy's
  own among them. Visits kept before this release have none.
- **How long**, machinery: `KEEP_IP_ADDRESSES_FOR` in
  `source/backend/visits/prune.ts`, as long as `KEEP_EVENTS_FOR` (90
  days) as it ships, or `"forever"`. The hourly `prune-analytics` runner
  blanks the address of every visit older than that, a batch at a time
  (`forgetOldAddresses`), and the visit stays its 25 months.
  `pruneAnalytics` answers `addresses` beside `events` and `visits`: a
  copy's own code or tests that read its answer take the new key.
- **The sample visits**, machinery: `source/database/seed/analytics.ts`
  gives the three remembered sample visits addresses set aside for
  documentation (RFC 5737 and RFC 3849), and the anonymous one none.
- **The docs**, machinery: `source/backend/visits/README.md` (what's kept,
  and "How long it's kept"), `source/frontend/visitors/README.md` ("What's
  never recorded", "Remembering a visitor"), `schema.ts`'s comments and
  `CLAUDE.md` say whose address is kept and for how long.
- **`START-HERE.md`'s question on remembering visitors** (step 1, item
  13), a starting point: it tells the owner the site keeps each visit's
  country and, for 90 days, the visitor's IP address, and that a visitor
  who isn't remembered has no address kept. A copy has already answered
  it, so the update changes only its "never the visitor's IP address" if
  it's still there.

Flags:

- **Schema**: generate the copy's migration with
  `pnpm database:generate --name=analytics-visits-ip-address`. squawk
  flags its `CREATE INDEX` on a table that has rows, so put these lines,
  written by hand, right before it (the dates are the template's: say
  when the copy took 0.7.0 if it was later):

  ```sql
  -- analytics_visits began with Foundation 0.7.0, on Nov 21, 2026, so a copy
  -- holds a few weeks of visits at most, and every one's ip_address was just
  -- added as null, so the index starts empty and building it is one short
  -- scan of the table
  -- squawk-ignore require-concurrent-index-creation
  ```

- **Owner**: a privacy notice that says the site never keeps a visitor's
  IP address, as 0.7.0 asked an owner to word it, is out of date once
  this deploys: the site keeps a remembered visitor's for 90 days. Ask the
  owner to reword it. An owner who wants no address kept at all, while
  still remembering visitors, has no setting for it yet: say so, and ask.

**How to tell a copy already has it**: `source/database/schema.ts` has
`ip_address: inet()` on `analytics_visits`, and
`source/backend/visits/prune.ts` exports `KEEP_IP_ADDRESSES_FOR`.
