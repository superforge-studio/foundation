# 0.20.0 (2026-11-23)

The app calls Superforge Infra through `@superforge/infra` 0.3.0, Infra's
v1 API. Infra's contract, every call's request and answer, is in the
package now, and the calls take their v1 shape: login names a channel and
an address, comments and Claude's connections name a person by their
user's ID, never their email, and every refusal is `{ reason, message, … }`,
the shape this app's own API answers in.

**Infra keeps no backward compatibility before v1, so take this release
when Infra moves to its v1 API**, before any other. Once Infra has moved,
a copy before this release can't log anyone in: its server still sends
the old shapes, which Infra refuses, so the login page says login isn't
working, the toolbar's comments don't reach the board, and Claude can't
connect. A copy that takes it before Infra has moved has the same trouble
the other way round.

- **The package**, machinery. `package.json` depends on
  `@superforge/infra` `^0.3.0`. Every refusal is Infra's own `error`, as it
  answered it, and an `invalid` carries `issues`, `[{ path, message }]`,
  in place of `fields`. The package's errors say why in the same shape,
  `reason: "unavailable"` with a `message`. **A copy's own code that makes
  a refusal by hand**, like a test's stub of Infra, gives it that shape.
- **Login**, machinery. `backend/auth/routes.ts` starts a login with
  `startLogin({ channel: "email", address, ip, link_to })`, where
  `link_to` is the page the email's link opens, this app's
  `${origin}/login`, and verifies one with `verifyLogin({ channel:
  "email", address, code })` or `({ token })`, which answers `{ channel,
  address }`. `/api/auth/start` still answers the address as `email`, so
  the pages read it as before. Infra's `too-soon` and `too-many` are one
  `rate-limited` now, with `limit` (`address`, `network` or `project`) and
  `retry_after`, which `/api/auth/start` answers 429 with `Retry-After`,
  as before. The login form (`whatWentWrong` in
  `frontend/components/site/login-form.tsx`) says to check the inbox for
  a `retry_after` of a minute or less, and how many minutes to wait
  otherwise. **A copy's own code that reads `too-soon` or `too-many`**,
  from `/api/auth/start` or from Infra, reads `rate-limited` and its
  `retry_after`.
- **Comments**, machinery. `backend/comments/routes.ts` sends Infra
  `user_id` (it was `user`), the team member's ID, and `user_name`, their
  first name as `access.ts` lists them, which the board shows beside the
  note.
  The package sends each to Infra's `POST /v1/board/comments`, under the
  board's prefix, in place of `/v1/comments`; nothing in the app names
  the path.
- **Claude's login**, machinery. Infra knows the person who let Claude in
  by their user's ID, which never changes, never their email:
  - `backend/agents/routes.ts` allows a request with `allowAgent(request_id,
    { user_id, scopes })`, and lists and ends someone's connections with
    `agentConnections(user.id)`, which answers each with `user_id` and
    `resource` in place of `email`. A refusal is told by its `reason`
    (`unavailable`, `not-found`, `not-asked`); there's no `.error` any
    more.
  - `backend/auth/agents.ts` checks a token with `checkAgentToken(token,
    { origin, resource })`, where `resource` is the app's own MCP,
    `${origin}${MCP_PATH}`, so a token Claude got for another address
    never opens this one. It answers `user_id`, which the app finds the
    user by (a token naming anything but a row's ID is refused before it
    costs a query), active, and then on the list by their slug
    (`listedBySlug`), as an API token's person is. A token stays its
    person's if the list changes their email.
  - `backend/agents/oauth.ts` hands `passOAuth` the call's name,
    `"metadata"`, `"authorize"`, `"token"`, `"register"` or `"revoke"`, in
    place of a path, with the package's `OAUTH_CALLS` and `APP_PATHS`
    (`/oauth`, and the Allow page at `/connect`), which
    `backend/infra/index.ts` exports. The package builds the server's
    metadata itself, with no call to Infra; the rest go to Infra's
    `/v1/agents/oauth/…`, and authorize sends the browser to the Allow
    page, `/connect/<request id>`.
  - `utilities/schemas/agents.ts` takes `AGENT_SCOPES`, `agent_scope` and
    `AgentScope` from Infra's contract, `@superforge/infra/contract`,
    which needs nothing of Node's, so the pages can import it too.
  - **A copy's own code** that calls any of these with an email, or a test
    that mints a token with `standInAgentToken({ email })`, gives the
    user's ID, and a token the address it's for: `standInAgentToken({
    user_id, resource: "http://localhost/admin/mcp" })`.
- **`INFRA_URL` is a dev server's alone**, machinery. A build always calls
  Infra at its own address, so no variable can send its secret key, or
  anyone's login, anywhere else. `.env.example` no longer lists it, and
  `backend/infra/README.md` says so. A dev server still reads it, to work
  on Infra itself.
- **The docs**, machinery: `backend/infra/README.md` has the calls in
  their v1 shape, `backend/mcp/README.md` how Claude's tokens are bound
  to `/admin/mcp`, and `CLAUDE.md`'s `auth/` and `comments/` entries
  follow.

**Owner**: everyone who connected Claude to the app connects it again,
once, after Infra moves: Infra's connections went by email, so it ends
them as it moves, and a token that names an email no longer logs anyone
in. Nothing changes in Railway: no variable is added, and `INFRA_SECRET_KEY`
stays as it is. If the app's service in Railway has `INFRA_URL` set, a
build ignores it now, and it can be deleted.

No other flags: no schema change.

**How to tell a copy already has it**: `source/backend/auth/routes.ts`
calls `startLogin` with `channel: "email"`, and
`source/utilities/schemas/agents.ts` imports from
`@superforge/infra/contract`.
