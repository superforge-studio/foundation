# 0.13.0 (2026-11-22)

The template says "log in" and "login", never "sign in". "Log in" is the
verb, two words (`Log in`, `Log out`, `logged in`, `logIn()`), and
"login" the noun, one word (`/login`, `login.ts`, "your login code").
Every page, button, email, name and doc moved together, so nothing says
both. "Sign up" stays.

**Superforge Infra moved first** (Nov 22, 2026): its login calls are
`POST /v1/login/start` and `/v1/login/verify` now, with nothing left at
`/v1/sign-in`, and its emails link to `/login#<token>`. **A copy before
this release can't log anyone in until it takes it**: its server still
calls `/v1/sign-in/start`, which Infra answers 404, and the login page
says login isn't working. Take this release first, before any other.

- **Infra's calls**, machinery: `source/backend/infra/client.ts` calls
  `/login/start` and `/login/verify`, and the stand-in's link is
  `/login#<token>` (`stand-in.ts`). The client's methods are
  `startLogin` and `verifyLogin`, and its answers' schemas
  `started_login` and `verified_login` (`answers.ts`).
- **The login page at `/login`**, machinery: `routes/sign-in.tsx` is
  `routes/login.tsx`, and every link to it says `/login`. Its tab's title
  is "Login"; its heading and buttons say "Log in", "Finish logging in"
  and "Log out". Nothing answers `/sign-in` any more, and nothing
  redirects it (no redirects before 1.0): a bookmark or a link to it
  stops working. **Owner**: a link to `/sign-in` on another site, in an
  email or in an ad goes to `/login` now.
- **The files that moved**, machinery: `backend/auth/sign-in.ts` is
  `login.ts`, `backend/auth/signed-in.ts` is `logged-in.ts`,
  `backend/tests/support/sign-in.ts` is `login.ts`, and
  `frontend/components/site/sign-in-form.tsx` is `login-form.tsx`.
- **The names**, machinery. A copy's own code that uses any of these
  renames it the same way:

  | Was                                          | Is                                         |
  | -------------------------------------------- | ------------------------------------------ |
  | `signedIn`, `maybeSignedIn` (middleware)     | `loggedIn`, `maybeLoggedIn`                |
  | `context.var.signed_in_with`                 | `context.var.logged_in_with`               |
  | `signIn()`, `maySignIn()`                    | `logIn()`, `mayLogIn()`                    |
  | `signInAs()` (tests)                         | `logInAs()`                                |
  | `SignInForm`, `SignInProof`, `SignedIn…`     | `LoginForm`, `LoginProof`, `LoggedIn…`     |
  | `startSignIn`, `verifySignIn`, `signOut`     | `startLogin`, `verifyLogin`, `logOut`      |
  | `sign_in_start`, `sign_in_code`, …           | `login_start`, `login_code`, …             |
  | `POST /api/auth/sign-out`                    | `POST /api/auth/logout`                    |
  | `POST /api/account/sessions/sign-out-others` | `POST /api/account/sessions/logout-others` |
  | a 401's `signed-out`                         | `logged-out`                               |
  | `useSession()`'s `signed-in` / `signed-out`  | `logged-in` / `logged-out`                 |
  | `ACCESS.sign_in` (`auth/access.ts`)          | `ACCESS.login`                             |

  `ACCESS` is the copy's own: keep its value (`"anyone"` or `"listed"`)
  under the new key. "Sign up" (`tell-team-of-sign-up`, the `signed-up`
  event) is unchanged, so no workflow or event is renamed.
- **The column**, machinery. **Schema**: `users.signed_in_at` is
  `logged_in_at` (`source/database/schema.ts`). drizzle-kit asks whether
  a column was renamed or dropped and added, which a script can't
  answer, so make the copy's migration with
  `pnpm database:generate --custom --name=users-logged-in-at`, put this in
  it:

  ```sql
  -- The template says "login", not "sign-in" (0.13.0)
  -- squawk-ignore renaming-column
  ALTER TABLE "users" RENAME COLUMN "signed_in_at" TO "logged_in_at";
  ```

  then change `"signed_in_at"` to `"logged_in_at"` in the snapshot it
  wrote (`meta/<number>_snapshot.json`), and check that
  `pnpm database:generate` finds nothing more to do. The version still
  serving writes the old name at each login until the new one starts, so
  a login in the minute the deploy takes fails, and its person tries
  again.
- **The words**, machinery: every comment, doc, test name and string
  that said sign in, signed in, sign-in or sign out. `CLAUDE.md` has a
  rule of its own, "Say log in, not sign in", beside American English, so
  an agent doesn't write "sign in" again. A copy's own copy (PRODUCT.md,
  its pages) is the owner's: say so to them, and change it only with
  their yes.

How to tell a copy already has it: `source/frontend/routes/login.tsx`
exists, and `client.ts` calls `"/login/start"`.
