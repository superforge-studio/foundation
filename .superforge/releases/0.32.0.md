# 0.32.0 (2026-11-25)

A copy's own goes in files of its own. The team, its roles, the Railway
project's names, the site's title, whom it remembers, how long things are
kept, Your files' limits, and any event, queue or webhook source a copy
adds were each written into one of the template's files, beside the
template's code. So every later release that touched one of those files
met what the business had written there as a conflict, and the update
guide's rule, that machinery takes the release's version, could undo it:
a copy that narrowed what a `member` may do got the template's `member`
back. Now each has a file of the app's own beside the template's, which
the template's reads and no release changes after this one. A minor,
since a copy moves its own entries once, by hand, in the update that
brings it (below). No schema change and no variable.

**Owner**: nothing to decide. The agent moves the copy's own entries
(below); the owner reviews the PR as with any update.

## The team and its roles (`source/backend/auth/access.ts`, `source/backend/auth/app.ts`, `source/utilities/permissions/`), machinery

- **`ACCESS`, the team and what each role may do, is in `auth/app.ts`**,
  beside `OTHERS`, whoever else logs in. `auth/access.ts` keeps only the
  template's: what a team member and a role are, and the checks on the
  list (`listedAs`, `problemsWith`, …). Everything that read `ACCESS`
  imports it from `auth/app.ts`.
- **A role's name on screen, and a role of the app's own, are in
  `utilities/permissions/`**: `ROLE_NAMES` and `TeamRole` there are the
  template's `owner` and `member` and then `APP_ROLES`, in
  `utilities/permissions/app.ts`, beside `APP_AREAS`, which both sides
  read. `TEAM_ROLES` and `TeamRole` are still exported by `access.ts`, and
  `ROLE_NAMES` by the dashboard's `words.ts`, so nothing that imports them
  changes.
- **An area a later release adds is the owner's alone in a copy** until
  the copy's `roles` give it, since `roles` are the copy's now: that
  release's notes say which role the template would give it.

**Moving a copy's own, in this update**: `access.ts` conflicts, since the
copy listed its team there. Take the release's `access.ts` whole. Then in
`auth/app.ts`, which the release rewrites, write the copy's own
`internal_users` and `roles` in place of the placeholders (Ada and
Grace), exactly as they were, and its own `OTHERS` if it had changed it.
A role the copy added to `TEAM_ROLES` goes in `APP_ROLES`
(`utilities/permissions/app.ts`) with the name it had in `ROLE_NAMES`,
and comes out of `words.ts`.

## Railway (`.railway/railway.ts`, `.railway/app.ts`), machinery

- **`.railway/app.ts` is the app's own part of the project**: its name,
  the repository, Railway's address for the app, the region, custom
  domains and the app's own variables (`APP`). `railway.ts`, the
  template's, reads it and keeps the rest: the database and its recovery
  bucket, the `Storage` bucket, the service's build, start, healthcheck,
  CDN and tracing, and the template's variables, with the app's own after
  them. Run as it ships, the two declare exactly what 0.31.0's file did.
- **A custom domain is `domains`**, which `railway.ts` makes the app's
  `customDomains`, only once there's one, so a copy without any declares
  none, as before.
- **The typecheck covers `.railway/`** (`tsconfig.json`), so a region
  Railway doesn't have, or a mistyped variable, fails `pnpm check` rather
  than the apply.

**Moving a copy's own, in this update**: `railway.ts` conflicts where
the copy named its project, repository, address and region, and wherever
it added a variable or a custom domain. Take the release's `railway.ts`
whole, then write the copy's own in `.railway/app.ts`: the project,
`github(…)`'s repository, the address in `serviceDomains`, the region
(the key it gave `REGIONS[…]`), each name under `customDomains` in
`domains`, and each variable it added in `env`, as it was (`preserve()`
from `railway/iac` for a secret). Then `railway config plan` shows no
change: the project as code is what it was.

## The settings (`source/utilities/settings/`), machinery

- **`SETTINGS` is what a business decides about its app**, which the code
  reads: the template's defaults, `TEMPLATE_SETTINGS` in `index.ts`, with
  the app's own over them, `APP_SETTINGS` in `app.ts`, which holds only
  what the app changes, so a setting a later release adds, or a default it
  changes, reaches the copy with nothing to merge.
- **What's in it**: `site_title` and `site_description`, every page's
  unless it sets its own (the root route read them from its own `head`);
  `visitor_mode` (was `VISITOR_MODE`, `utilities/visitors.ts`);
  `keep_finished_runs_for` (was `KEEP_FINISHED_FOR`, `engine.ts`);
  `keep_events_for`, `keep_ip_addresses_for` and `keep_visits_for` (were
  the constants in `visits/prune.ts`, which still export them, read from
  the settings); `keep_webhook_deliveries_for` (likewise,
  `webhooks/prune.ts`); and `largest_file`, `trash_days` and `link_days`
  (likewise, `utilities/schemas/files.ts`). The addresses are kept as long
  as the events unless `keep_ip_addresses_for` says, as before.
- **"A file is at most 100 MB"** follows `largest_file`
  (`LARGEST_FILE_WORDS`), and the template's tests of how long the
  analytics and the deliveries are kept check the template's defaults, so
  a copy that changes a setting doesn't fail them.

**Moving a copy's own, in this update**: wherever the copy changed one of
these from the template's (its title and description in `__root.tsx`, its
`VISITOR_MODE`, a `KEEP_…`, a file limit), take the release's file, and
set the same value in `APP_SETTINGS` (`source/utilities/settings/app.ts`).
One the copy left as the template had it stays out.

## Events, queues and webhook sources (`source/backend/workflows/app-events.ts`, `source/backend/webhooks/app.ts`), machinery

- **The app's own events and queues are in `workflows/app-events.ts`**,
  `APP_EVENTS` and `APP_QUEUES`, which `EVENTS` and `QUEUES` take after
  the template's. A file of their own, not `workflows/app.ts`: that one
  imports the app's workflows, and what they import reads the events as it
  loads, so they'd load in a loop.
- **The app's own webhook sources are `APP_SOURCES`**, in
  `webhooks/app.ts`, which the API hands its routes. `sources.ts` keeps
  the types and helpers, and no longer exports `SOURCES`: the template has
  no source of its own.

**Moving a copy's own, in this update**: an event the copy declared in
`events.ts` goes in `APP_EVENTS`, a queue in `queues.ts` goes in
`APP_QUEUES`, and the sources in `sources.ts`'s `SOURCES` go in
`APP_SOURCES`. Anything that imported `SOURCES` imports `APP_SOURCES`
from `webhooks/app.ts`.

## The dashboard's own Settings parts (`source/frontend/components/dashboard/app.ts`), machinery

`APP_SETTINGS` there, this app's own parts of the Settings screen, is
`APP_SETTINGS_PARTS`, so it isn't taken for the app's settings above. A
copy that listed a part renames it.

## The guides

`workbench/writing-code.md`'s table of the app's own has a row for each,
and its "Each part's own guide" says a feature of the app's gets its line
under "This app's own" in `CLAUDE.md`, never in that table.
`START-HERE.md`'s steps 3 and 5, `workbench/commit-and-deploy.md`'s
Railway setup, domains and variables, and the guides for logging in, the
workflows, the webhooks, the analytics, the pages' script, Your files, the
dashboard and Railway say where each lives now, and so does `CLAUDE.md`'s
list.

How to tell a copy already has it: `source/utilities/settings/index.ts`
exports `SETTINGS`, and `.railway/app.ts` exports `APP`.
