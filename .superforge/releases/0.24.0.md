# 0.24.0 (2026-11-24)

The cleanup ahead of 1.0.0: what was kept only for earlier releases goes,
with exports and a dependency nothing used, the schema's fixed lists all
get their checks, a file's size gets room to grow, a folder can no longer
be deleted from under its files, and a deploy's stop gets the time it
needs. A minor, since it removes a workflow and an event, and changes how
a folder's row is deleted. Flags: **Schema**, **Railway**.

## Before updating: runs of `tell-team-of-sign-up`

**`tell-team-of-sign-up` and its event `user-signed-up` are gone**
(`source/backend/users/workflows.ts`, `source/backend/workflows/events.ts`,
`source/backend/workflows/index.ts`). Nothing in the template has started it since only the team logs in.
DBOS leaves a run whose workflow isn't registered pending for good, so
before taking this release, check that no run of it is waiting:

```bash
pnpm database:sql "select workflow_uuid, status from dbos.workflow_status where name = 'tell-team-of-sign-up' and status in ('PENDING', 'ENQUEUED')"
```

and the same on production's database (its Data tab on Railway). Any row
there is a run from before then: let it finish on the current release,
or cancel it from the Workflows screen, before updating. Its finished runs
stay on the Workflows screen under its name; a failed one can no longer be
run again (`retry` in `source/backend/workflows/engine.ts` now answers a
run of any workflow that's no longer listed as not found). A copy that
kept the workflow on purpose, or its event, keeps its own lines. Machinery.

How to tell a copy already has it: `grep -r tellTeamOfSignUp source`
finds nothing.

## The schema (`source/database/schema/foundation.ts`), machinery — Schema

Generate the copy's migration with `pnpm database:generate`, then edit it
as the template's `0010_cleanup-checks-and-file-sizes.sql` is: the two
analytics checks `NOT VALID`, and the `files` lines with the
`-- squawk-ignore` comments and their reasons, so `pnpm database:check`
passes.

- **`files.size` is a `bigint`** (`mode: "number"`), so a copy can raise
  the 100 MB limit past 2 GB. Every row fits.
- **`files.folder_id` is `on delete restrict`**, from `cascade`: a folder's
  row can't be deleted while a file's row is in it, since the file's bytes
  would stay in the bucket with nothing pointing at them. Trash already
  deletes files before their folders (`emptyExpired`), and the seed now
  deletes `files` before `file_folders`. **A copy with code or scripts of
  its own that delete folders** has them delete the files inside first,
  bytes then rows; check with `grep -rn "delete(file_folders)" source`.
- **`analytics_events.source` and `analytics_visits.device` have checks**
  made from `EVENT_SOURCES` and `DEVICES`, as every other fixed list has
  (`analytics_events_source_check`, `analytics_visits_device_check`). They
  go in `NOT VALID`, so the migration doesn't scan a big analytics table:
  they hold for every row written from now on. To check the rows already
  there first, on a copy with data:

  ```sql
  select count(*) from analytics_events where source not in ('browser', 'server');
  select count(*) from analytics_visits where device not in ('mobile', 'tablet', 'desktop');
  ```

  Both are 0 unless the copy's own code wrote something else, which the
  copy then adds to the list.
- **`api_tokens.scopes`' check is made from `API_TOKEN_SCOPES`**
  (`source/utilities/schemas/api-tokens.ts`), the app's own list, `read`
  and `act`, no longer from `@superforge/infra`'s `AGENT_SCOPES`, so a
  release of the package can't change the schema. The check's SQL is the
  same, so it needs no migration. `utilities/tests/api-tokens.test.ts`
  checks the list holds every one of Claude's scopes.
- **`oneOf()`** in `source/database/columns.ts` makes a fixed list's check;
  `files.state` and `webhook_deliveries.outcome` use it too, with the same
  SQL. A copy's own tables can use it.

## Deploys (`.railway/railway.ts`, `source/node.ts`), machinery — Railway

- **Railway gives the old deployment 30 seconds to stop**
  (`drainingSeconds: 30`), and starts a crashed server again, up to ten
  times in a row (`restartPolicyType: "ON_FAILURE"`). Free; CI's apply
  makes the change. The server gives up on its stop after 25 seconds
  (`STOP_DEADLINE_MS`), logging that it did.
- **The workflows' gate keeps its connection alive** (`keepAlive` in
  `engine.ts`), so a connection that dies silently fails and frees the
  lock, rather than leaving the process running the workflows while
  another takes the gate. A failed restart of the workflows is logged
  rather than left unhandled.
- **A tab open across a deploy loads the page again** when it asks for a
  page's code the new build doesn't have (`vite:preloadError`, in
  `source/frontend/router.tsx`), once the page has been open ten seconds.
- **CI's `railway-apply`, the job with production's token, pins its three
  actions to commits** (`.github/workflows/ci.yml`); Dependabot moves
  them.
- The comment on the day's visitor salt (`backend/visits/visitors.ts`)
  says what two processes making it at once really cost, and
  `workbench/commit-and-deploy.md`, "Domains", says why a proxy in front
  of Railway (Cloudflare's orange cloud) gives every visitor the same
  address.

## The local Postgres and the seed, machinery

- **A checkout's `.postgres/` from another major version of Postgres is
  made again** as the server starts (`source/database/local/server.ts`),
  rather than failing until `pnpm database:reset`.
- **`pnpm database:seed` deletes the last seed's file bytes** in
  `.storage/files/` before keeping the new ones.
- `workbench/writing-code.md` says `pnpm database:sql`'s session is
  read-only by default, which a query can turn off.
