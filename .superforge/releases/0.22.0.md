# 0.22.0 (2026-11-23)

Eight small bugs that writing the guides for Your files and logging in
found, each fixed with a test and its guide put right, and
four rough spots that updating copies found. A minor, since three change
how something works: the app's own answers are asked before `/api`,
taking someone off the team revokes their API tokens for good, and Trash
is emptied on a schedule rather than when someone looks.

## Your files (`source/backend/files/`), machinery

- **Folders go at most 32 deep, and nothing goes deeper.** Making a folder
  past `DEEPEST`, or moving one where it, or a folder inside it, would go
  deeper, is 409 `too-deep` (`create.ts`, `change.ts`, and `levelsOf` in
  `find.ts`, which counts the levels a move takes with it). Before, the
  33rd was made, 201, and then answered 500 to everything.
- **`GET /api/files/kept/:folder?under=`**: the kind's own folder
  (`visitor-salt/`) lists it, as leaving `under` out does, and a file's
  path is 404, not 500.
- **`PUT /api/files/uploads/:file_id` answers only in a dev server**,
  whose folder can't sign a form. Where the bucket can, as in a build, an
  upload goes straight to it, and the route is 404, so the server never
  reads a file into memory there.
- **The check for another site's forms looks only at a `POST`**, the one
  method a form sends (`backend/index.ts`), so a script's `PUT` of a text
  file, or curl's `--data`, is no longer 403 `forbidden` without an
  `Origin`. A form's `POST` from another site is refused as before.
- **Trash is emptied each hour, by a workflow**: `empty-trash`
  (`files/workflows.ts`, new, in `WORKFLOWS`), quiet, at a quarter past,
  calling `emptyExpired`, as `prune-webhook-deliveries` does its own
  prune. `GET /api/files/trash` and `POST /api/files/uploads` no longer
  run it, so a `GET` never deletes anything for good.

## Logging in (`source/backend/auth/`, `source/backend/users/`), machinery

- **Taking someone off the team ends every way they were in, for good**
  The sync (`users/sync.ts`) deletes their API tokens
  with their sessions, so a token never works again if they're listed
  again: they make new ones. Claude's tokens are Infra's, signed rather
  than kept here, so as the server starts, `endConnectionsOfGone` asks
  Infra to end every connection Claude has as anyone deactivated
  (`endAgentConnections`, `@superforge/infra` 0.3.0): Claude can't
  refresh one, and what it holds runs out within minutes. An Infra that
  doesn't answer is logged (`Claude's connections weren't ended`) and
  asked again at the next start.
- **`maybeLoggedIn` holds a token to its scopes**: a token with only
  `read`, sent with anything but a `GET` or a `HEAD`, is nobody's, so the
  route answers it as a visitor. Recording a visit works as before.
- **The seed never reaches production**, which a test now holds
  (`database/seed/tests/seed.test.ts`): it writes only this checkout's
  own Postgres, nothing the server runs imports it, and no script but
  `database:seed` runs it. `source/database/README.md` says so.

## The server (`source/server.ts`), machinery

- **The app's own answers are asked first** (`appAnswer`,
  `source/app.ts`), before `/api`, the MCP, Claude's login and the pages,
  so a copy can answer a path under `/api` on a host of its own. A copy
  whose `appAnswer` answers nothing, as the template ships, is unchanged.
  One that answers broadly now sees `/api` too: it returns null for the
  API's own paths on the site's host. `source/app.ts` is the copy's own,
  and only its comment changes; a copy that has changed the comment
  keeps its own.

## Updates (`.superforge/superforge.json`, `CLAUDE.md`, `workbench/updating.md`), machinery

- **`superforge.json` stops conflicting on every release.** `version` is
  now its first line and `project_id` its last, null until the app is on
  Infra, with `template` between, so a release's new version and a copy's
  own ID never touch the same lines. **This update conflicts on it once**,
  from the old layout, where `project_id` was added after `version`:
  write it as the release has it, with the copy's `project_id`, or null
  if it has none.
- **`CLAUDE.md` has a place for the app's own areas**: "This app's own",
  at the end of Project Architecture, which no release changes, and "Keep
  things current as you go" and "Keeping this list current" send a
  copy's areas there. **This update**: take the release's bullets, and
  move each of the copy's own areas, and what it wrote into the
  template's bullets, into "This app's own", once.
- **`workbench/updating.md`** says how an update handles each of the two
  files, and leaves out `source/frontend/components/welcome/`, which
  `START-HERE.md` deletes with the home page, so a release that changes
  it no longer stops at `does not exist in index`.

## Tests, machinery

- **A test's own Hono app gets the test API's whole `context`**:
  `withVariables` (`backend/index.ts`, new), which `apiWith()` puts the
  variables on `context` with, and `testApi().variables`. The two tests
  that set `database` and `access` by hand take them, so a copy's own
  variables reach them too.

A copy takes all of it as it is, with the two files above resolved as
they say. No schema change, variable or secret.

**How to tell a copy already has it**: `source/backend/files/workflows.ts`
exists, and `.superforge/superforge.json`'s first key is `version`.
