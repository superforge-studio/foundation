# 0.39.0 (2026-11-26): ship what you're asked to change, merge and all

An agent asked for a change used to open the PR only once told to ship,
and merge it only once told to merge, so every change ended with the owner
typing "merge it". Now being asked for a change is being asked to ship
it: the agent pushes, opens the PR and merges it once `check` passes. Only
a PR whose merge a revert can't undo waits for the owner's go. A minor,
since how a copy's agent ships changed. No schema change, no variable, no
secret, no Railway change.

**Owner**: nothing to do. From this release, a change you ask for is live
once its checks pass, without a second ask. Say "just the PR" or "don't
merge yet" when you want to look first.

## The rule (`workbench/commit-and-deploy.md`, "Pull requests"), machinery

- **What you're asked to change, you ship**: "fix this", "add that", "yes,
  make the change" and "open a PR" each mean push, open the PR and merge
  it once `check` passes. A question, an investigation or a plan ships
  nothing until the owner says yes.
- **Merge once every check on the PR's latest commit has passed**, never
  on one pending or failed, or on an empty list, and without counting on
  GitHub to refuse, since a repository without the `main` ruleset merges a
  failing PR.
- **A PR waits for the owner's go** only when it has a migration (anything
  in `source/database/migrations/`), changes production's data as it
  deploys (a shorter retention, code that rewrites rows as it starts),
  adds or removes a Railway resource or variable in `.railway/`, or needs
  a step only the owner can take first (a secret, a DNS record, tracing).
  The agent opens it, watches `check`, says what it's waiting on, and
  merges once they say so.

## Where else it's said

`CLAUDE.md`'s hook for committing and shipping says the same, and "Keep
things current" asks for the PR whatever the task. `workbench/updating.md`,
step 5: an update merges as any PR does. `README.md`, "Updates": the same,
for the owner. `workbench/setup/3-ship.md` and `4-make-it-theirs.md`: the
setup's PRs merge once `check` passes, without the owner's go; a copy
that's set up has neither file.

**How to tell a copy has it**: `workbench/commit-and-deploy.md` says "A PR
waits for the human's go only when merging it does what reverting it
can't undo."
