# 0.9.0 (2026-11-22)

Each release's notes in a file of their own, so an update reads only the
releases it takes. Until now every release was a section of
`CHANGELOG.md`, which grew by hundreds of lines a release, and an update
read all of it to find the few after the copy's version. Nothing in the
app changes.

- **A file per release**, machinery: `.superforge/releases/<version>.md`,
  headed `# 0.9.0 (2026-11-22)`, beside `.superforge/superforge.json`.
  Every release before this one is there too, its notes as they were.
- **`CHANGELOG.md` is their index**, machinery: a line per release,
  newest first, each linking its file.
- **`workbench/updating.md`**, machinery: how a release is written, which
  was `CHANGELOG.md`'s, is now its own section there, beside where the
  releases are and how to see whether a newer one is out
  (`git ls-remote`, with nothing fetched). An update reads each release
  after the copy's from its own file, at the latest tag.
- **`release-tag`**, machinery, though a copy never runs it: it tags a
  version only once `.superforge/releases/<version>.md` has its heading
  and `CHANGELOG.md` its line.

How to tell a copy already has it: `.superforge/releases/` exists.
