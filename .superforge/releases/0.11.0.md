# 0.11.0 (2026-11-22)

The app traces itself into Railway. Railway's edge already traced each
request to a traced service, but nothing inside the app was seen: now
every request the server answers, every query and every call out is a
span, each workflow run is a trace with a span per step, and what's logged
inside one is kept on it, so an agent reads production's traces and logs
through the Railway MCP (`list-traces`, `get-trace`, `get-logs`).
Railway's tracing is a preview, behind the account's Tracing beta, and the
app's tracing is on only while Railway says where its collector is, so
anywhere else it does nothing.

- **The tracing setup**, machinery: `source/tracing.ts`, new, which
  `pnpm start` loads with `--import` ahead of `source/node.ts`.
  OpenTelemetry, traces only, on while Railway's `OTEL_EXPORTER_OTLP_*`
  variables are set, or with `OTEL_TRACES_EXPORTER=console`, which prints
  each span, for `pnpm preview`. It instruments Node's `http`, `fetch`
  (undici) and `pg`, the app's queries and DBOS's, inside whatever span is
  running (import-in-the-middle hooks only those modules), redacts the
  query parameters that carry a credential (`REDACTED_QUERY`: OAuth's
  `code` and `state`, any `token` or `email`, and signed URLs'), and keeps
  what's logged while a span runs on it, as an event, with `{ trace_id }`
  on the log line. `source/node.ts` names a request for one of the build's
  files by its path, and sends the last spans on SIGTERM
  (`stopTracing()`). New dependencies: the `@opentelemetry/*` packages
  and `import-in-the-middle`, in `package.json`.
- **Spans named by route**, machinery: `source/utilities/tracing.ts`, new.
  `traceRoutes`, a Hono middleware, goes first in each app the server
  hands requests to (`backend/index.ts`, `backend/mcp/index.ts`,
  `backend/agents/oauth.ts`) and names each request's span for the route
  that answered it, `GET /api/workflows/runs/:id`, and a request the MCP's
  `call_api` makes in-process a span inside the MCP's. `nameRequest` is
  for a route that answers many addresses with one handler, `traced` for
  work worth a span of its own, `recordError` marks the running span
  failed, which `backend/failures.ts`'s `answerUnexpected` calls, and
  `tracingOn` says whether this process traces. `source/server.ts` names
  the dashboard `/dashboard/*` and the Allow page `/connect/:request_id`.
  A copy with a Hono app of its own that `server.ts` hands requests to
  adds `.use(traceRoutes)` first in it, and one whose links carry a
  credential or a person's details in their query adds the parameter to
  `REDACTED_QUERY`.
- **Workflow runs and steps**, machinery: `backend/workflows/engine.ts`
  sets DBOS's `tracingEnabled` while the process traces, with
  `otelAttributeFormat: "semconv"`, so each run is a span named for its
  workflow, each step one inside it, and each carries
  `dbos.operation.workflow_id`. `backend/workflows/runners.ts` traces each
  turn of a runner a minute or more apart, as `runner <name>`.
- **Tracing on in the Railway project**, machinery:
  `tracing: { enabled: true }` on the app's service in
  `.railway/railway.ts`, which has Railway's edge trace the app's
  requests and its next deploy set the `OTEL_*` variables. Not
  `autoInstrumentation`, which would trace each request twice.
- **The smoke test checks it**, machinery: `workbench/scripts/smoke-test.mjs`
  runs the build against a collector of its own, as Railway's variables
  set it up, and fails unless the spans arrive as OTLP protobuf with the
  header, holding `GET /api/health` and a `pg.query`.
- **The docs**: `workbench/writing-code.md`'s "Logging" is now "Logging
  and tracing", with what's traced, how to add a span, what never goes in
  one, and how to read production's; `CLAUDE.md` has a hook for
  investigating production, and `source/tracing.ts` and
  `utilities/tracing.ts` in its list; the workflows README and
  `workbench/commit-and-deploy.md` say what's traced and which variables
  Railway sets.

**Railway**: the tracing switch in `.railway/railway.ts`. Railway's CLI
docs say a project token, which CI's `railway-apply` uses, can read
traces but can't turn tracing on or off. A new copy's first apply is run
by hand, logged in with `railway login` ("Setting up Railway", step 3), so
it turns tracing on there. **A copy that updates** turns it on with its
owner's login before the update merges, so CI's apply finds nothing to
change: from the copy's checkout, logged in with `railway login`,

```bash
railway trace enable --service app --environment production
```

or the Railway MCP's `set-service-tracing`, which redeploys the running
code with Railway's `OTEL_*` variables. Railway's tracing is a preview:
whether it needs the account's Tracing beta (Account → Feature Flags) is
untested, and if the command refuses, turn that on first. What tracing
costs isn't published yet.

How to tell a copy already has it: `source/tracing.ts`, and
`--import ./source/tracing.ts` in `package.json`'s `start`.
