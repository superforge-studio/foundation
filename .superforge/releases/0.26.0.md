# 0.26.0 (2026-11-24)

The `main` ruleset is in the codebase. Setting it was the owner's, by
hand, in GitHub's settings; it's now a file, as Railway is, and a command
an agent runs.

- **The ruleset**, machinery: `.github/rulesets/main.json` holds the `main`
  ruleset as GitHub's API takes it: `main` can't be deleted or
  force-pushed, it changes through a pull request with no approvals, and
  CI's `check` has to pass first. `pnpm github:ruleset`
  (`workbench/scripts/ruleset.sh`) puts it on the repository as whoever
  `gh` is logged in as: it makes the ruleset, or makes the one named
  `main` match the file, so it's safe to run again.
- **Without rulesets**: GitHub has them on a private repository only from
  Pro or Team up. On a plan with none, the command says so and passes.
  Nothing else depends on the ruleset: CI runs and Railway deploys the
  same without it.
- **The guide**: `workbench/commit-and-deploy.md`, "Setting up Railway",
  step 5 is the command, an agent's, no longer the human's.

**After the update**, the agent runs `pnpm github:ruleset` once, from
the copy's root, with the owner's `gh` login: nothing for the owner to
click. A copy that already has a ruleset named `main`
gets it replaced by the file's, which is what the guide had the owner set
with deleting and force-pushing `main` refused too; a copy whose ruleset
has another name keeps it beside the new one, so delete the old one in
Settings → Rules, or rename it `main` first. A copy that requires more
than `check` adds its checks to its own `.github/rulesets/main.json`
before running it.

No flags: no schema, no variable, no deploy order.

**How to tell a copy already has it**: `.github/rulesets/main.json`
exists, and `package.json` has the `github:ruleset` script.
