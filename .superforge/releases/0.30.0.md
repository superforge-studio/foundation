# 0.30.0 (2026-11-25)

A row of the team is a slug with an address, and an address handed on no
longer carries anything with it. Before, an owner who replaced someone by
editing their entry in `access.ts` (the same slug, a new name and address)
left the previous person logged in, as the new one, with API tokens that
never run out and Claude's connections; a new slug listed with an address
a departed person's row still held took over that row, with its ID and
its history; and an address a deactivated row held, given to someone
listed, failed the server's sync at every start and made their login a
500 until someone edited the database by hand. Now every way in an old
address had ends with it, a new slug always gets a row of its own, and an
address is unique among the active team only. A minor, since it changes
how the team's rows follow the list, and someone whose own address
changes is logged out once. Flags: **Schema**.

## Before updating: whose address the copy's list changes

Anyone whose address the copy changes in `access.ts`, in the same update
or later, is logged out everywhere at the deploy, their API tokens are
revoked, and Claude's connections as them are ended: they log in again at
the new address, make new tokens and allow Claude again. Tell the owner
before deploying an update that also changes someone's address. A list
that changes no one's address changes nothing for anyone.

## The team's rows (`source/backend/users/sync.ts`, `source/backend/auth/login.ts`, `source/backend/auth/routes.ts`), machinery

- **`keepListed(database, listed, cleared)` finds a row by its slug
  alone**; the lookup by address, for a row from before slugs, is gone.
  Anyone else active with the listed address is set aside first
  (deactivated, with their sessions and API tokens ended). A row that has
  to come back, deactivated or with another address than the one listed,
  takes the listed address, with its sessions and API tokens ended, only
  when it's in `cleared`, the rows Infra has said Claude has no connection
  as; otherwise it stays set aside, and the answer is `not-cleared`. It
  answers an `OperationResult` now, with `came_back` beside `id` and
  `made`.
- **`syncInternalUsers(database, infra, access)` takes Infra.** It asks
  Infra to end Claude's connections as each row coming back
  (`comingBack`, `clearConnections`), then, in one transaction, sets aside
  every active row the list doesn't have as it is, so an address handed
  from one listed person to another, or two people swapping theirs, works
  in any order of the list; keeps each listed person; and ends every
  deactivated person's sessions and API tokens, as before. A row Infra
  didn't clear waits, set aside, for the next start or its person's login.
  It answers `{ listed, made, deactivated, waiting }`, `waiting` being
  new, and `syncAppInternalUsers` passes the app's Infra.
- **A row listed again comes back only once Infra has ended Claude's
  connections as it**, as a row with a new address does. Before, someone
  listed again before Infra had answered found a connection still working.
- **`logIn` takes `infra`** in its options, and has Infra end Claude's
  connections as a row coming back before its transaction. When Infra
  doesn't, it answers `unavailable`, which `/api/auth/verify` answers 503
  `unavailable`, with the cause for the team.

A copy whose own code calls `syncInternalUsers`, `keepListed` or `logIn`
passes the new arguments, and treats `keepListed`'s answer as a result.

How to tell a copy already has it: `source/backend/users/sync.ts` exports
`clearConnections`.

## The checks (`source/backend/auth/access.ts`, `logged-in.ts`, `api-tokens.ts`, `agents.ts`, `source/backend/users/list.ts`), machinery

**A session, an API token and Claude's token count only while the list
has their row as it is: its slug, with its address** (`listedAs`, beside
`listedBySlug` in `access.ts`, with `addressOf`, a listed person's address
trimmed and lowercased). So what an old address let in stops at the deploy
that changes it, before the server's start ends it. The admin's Settings
counts someone as listed the same way. A copy's own check of who's asking
that used `listedBySlug` on a row uses `listedAs`.

How to tell a copy already has it: `access.ts` exports `listedAs`.

## The schema (`source/database/schema/foundation.ts`), machinery — Schema

**`users.email` is unique among active rows only**: the constraint
`users_email_unique` is replaced by the partial unique index
`users_email_index`, `where deactivated_at is null`, so a deactivated row
keeps its address, and someone listed later may take it. Generate the
copy's migration with `pnpm database:generate`, then give it the comments
the template's `0011_users-email-among-the-active.sql` has, so
`pnpm database:check` passes:

```sql
-- An address is unique among the active team only, so a deactivated row
-- keeping its address no longer stops someone listed from taking it. The
-- version still serving finds a row by its address only when its slug has
-- none, and gives no active row an address another active row has, so it
-- runs as before with the narrower index.
-- squawk-ignore ban-drop-constraint
ALTER TABLE "users" DROP CONSTRAINT "users_email_unique";--> statement-breakpoint
-- users holds the team, a few dozen rows at most
-- squawk-ignore require-concurrent-index-creation
CREATE UNIQUE INDEX "users_email_index" ON "users" USING btree ("email") WHERE "users"."deactivated_at" is null;
```

How to tell a copy already has it: `schema/foundation.ts` has
`uniqueIndex("users_email_index")`.

## Still open

Claude's access token lasts ten minutes, and the app checks it without
asking Infra, so one Claude already holds as a row can work until it runs
out after the row takes a new address. Closing that needs the token's
time of issue from `@superforge/infra`, and a column to compare it with.
