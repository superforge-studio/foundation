# 0.35.0 (2026-11-25)

The names a copy writes into its own files, settled before 1.0.0. The
team's list was `internal_users`, a name from when there were external
users beside them. There aren't any now, and everything newer already says
team (`TEAM_ROLES`, the `team` area, the Team screen), so the list is
`team`, and the code that reads it says team too. And two of Your files'
settings were counts of days in a file where every other length of time is
in milliseconds. A copy that wrote `keep_events_for: 90` meaning days would
have kept its events for 90 milliseconds. Now all of them are in
milliseconds. And the template's own code was `starter-template`, kept apart
from its name in case the name changed. It won't, so the code, the
repository and the template's own Railway project say `foundation` too. A
minor, since a copy renames a key in its own `auth/app.ts`, and sets
`template` in its `.superforge/superforge.json`, by hand, in the update
that brings it (below). No schema change and no variable.

**Owner**: nothing to decide. The agent renames the copy's own (below);
the owner reviews the PR as with any update.

## The team's list (`source/backend/auth/access.ts`, `source/backend/auth/app.ts`, `source/backend/users/`), machinery

- **`ACCESS.internal_users` is `ACCESS.team`**, and a person on it, the
  type `InternalUser`, is a `TeamEntry`.
- **What reads the list says team**: `listedInternal` is `listedByEmail`,
  beside `listedBySlug` (`access.ts`); `syncInternalUsers` is `syncTeam`,
  and `syncAppInternalUsers`, which `source/server.ts` exports and
  `source/node.ts` calls, is `syncAppTeam` (`users/sync.ts`); and
  `internalEmails` is `teamEmails` (`users/find.ts`).
- **The tests' API** has the list as `api.team`, where it was
  `api.internal_users` (`backend/tests/support/api.ts`).
- **The seed's sessions** are `sample-session-team`,
  `sample-session-team-phone` and `sample-session-team-expired`. Run
  `pnpm database:seed` again to log in with them.
- **The Settings screen's and Your account's prompts** for Claude Code
  name `ACCESS.team`.
- Everything that's a row stays as it was: the `users` table, `user_id`,
  `context.var.user`, `/api/users`, `backend/users/` and `user-added`. The
  team is the list in code, and a user is one of them as a row.

**Moving a copy's own, in this update**: `auth/app.ts` is the copy's own,
so the update doesn't change it, and the typecheck fails until it's done.
In `ACCESS` there, rename `internal_users:` to `team:`, keeping the list
exactly as it is. Then rename the same way anything of the copy's own
that used the old names, which this finds:

```bash
git grep -nE "internal_users|InternalUser|listedInternal|syncInternalUsers|syncAppInternalUsers|internalEmails|sample-session-internal"
```

## Your files' two lengths of time (`source/utilities/settings/`, `source/utilities/schemas/files.ts`, `source/backend/files/`), machinery

- **`trash_days: 30` is `keep_trash_for: 30 * DAY`**, how long something
  stays in Trash before it's deleted for good, beside `keep_events_for`
  and the rest.
- **`link_days: 7` is `links_last_for: 7 * DAY`**, how long a link from
  "Copy a link" works: a week at most, the longest a link from the bucket
  can be signed for.
- `utilities/schemas/files.ts`'s `TRASH_DAYS` and `LINK_DAYS` are
  `KEEP_TRASH_FOR` and `LINKS_LAST_FOR`, in milliseconds.
- The settings file's header says every length of time in it is in
  milliseconds, written with `DAY`.

**Moving a copy's own, in this update**: a copy that set `trash_days` or
`link_days` in its `APP_SETTINGS` (`utilities/settings/app.ts`) renames
the key and multiplies by `DAY`: `trash_days: 60` is
`keep_trash_for: 60 * DAY`. The typecheck catches the old keys.

## The template's name (`.superforge/superforge.json`, `source/utilities/template.ts`, the docs), machinery

- **The template's code is `foundation`**, where it was
  `starter-template`: `template` in `.superforge/superforge.json`,
  `package.json`'s `name`, and the generator tag's lookup (`template.ts`),
  which says `Superforge Foundation (https://superforge.studio/foundation)`
  as before.
- **Its repository is `superforge-studio/foundation`**, where it was
  `superforge-studio/starter-template`, whose address GitHub sends to it:
  `README.md` (titled "Superforge Foundation"), `SECURITY.md`, `LICENSE`,
  `START-HERE.md`, the home page's link and `workbench/updating.md`.
- **The template's own deployment** in `.railway/app.ts` is the Railway
  project `superforge-foundation`, at
  `superforge-foundation.up.railway.app`. A copy replaced these with its
  own on its first day.

**Moving a copy's own, in this update**: set `template` in the copy's
`.superforge/superforge.json` to `foundation`, the one time an update
changes more there than `version`. The update guide fetches the template
from the repository it names, and the generator tag looks it up: a copy
still on `starter-template` credits plain `Superforge`. Leave
`.railway/app.ts` as the copy has it, since its names are its own.

`START-HERE.md`'s step 3, `workbench/writing-code.md`'s "The team and
