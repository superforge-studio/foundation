# 0.29.0 (2026-11-24)

`@superforge/infra` 0.5.0, the surface the package keeps at 1.0.0. The
package brings its own zod, so the app's zod can move to the next major
without waiting for it. It exports fewer names: functions, constants and
types from its root, and the schemas of what Infra is sent at
`@superforge/infra/contract`. And it reads Infra's answers tolerantly, so
Infra can add a sending limit or a scope for Claude without breaking an
app that hasn't updated.

- **`@superforge/infra` `^0.5.0`**, machinery: `package.json`, with the
  lockfile. Nothing the template calls changed. What the release took
  away, and none of the template's code imported: `oauthMetadata`,
  `INFRA_URL`, `PACKAGE_VERSION`, `WaitingLogin`, the stand-in's `waiting`
  and `logs` options, every zod schema from the root, and from
  `/contract` the refusal schemas, the answers no one imported and the
  field schemas, `agent_scope` among them. A copy's own code that imported
  one of those changes it: a scope's schema is built as below, and the
  rest has no use outside the package. A 429's `limit` (`/api/auth/start`
  passes it through) is now any name, where it was `address`, `network` or
  `project`.
- **Claude's scopes, built with the app's own zod**, machinery:
  `source/utilities/schemas/agents.ts` builds `agent_allow` from
  `z.enum(AGENT_SCOPES)`, where it put the package's `agent_scope` inside
  it. The package's schemas are made with its own zod, which can be
  another version than the app's, and one zod's schema can't go inside
  another's. `backend/mcp/index.ts` already built its list this way.
- **`source/backend/infra/README.md`**, machinery: "In this folder" says
  the package brings its own zod, and that its schemas are never put
  inside the app's.

No flags: no schema, no variable, nothing for the owner to do.

**How to tell a copy already has it**: `package.json` asks for
`@superforge/infra` `^0.5.0`, and `source/utilities/schemas/agents.ts`
has `z.enum(AGENT_SCOPES)`.
